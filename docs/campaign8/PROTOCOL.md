# Campaign 8 execution protocol

## Evidence classes

LIVE means the actual existing backend or independently queried owner endpoint. CONTROLLED means original production application/services with disposable data and explicit mock adapters for unsafe external leaves. Native WebView2 screenshots are actual desktop evidence. Browser-only previews and source inventories are not native outcomes. Emulated WebView device scale is not evidence of changing physical Windows DPI. Every control outcome must state its class and authority.

## Isolation and ownership

No owner memories, conversations, configuration, credentials, model deployments, calendar vault or unrelated processes are modified. Native preference/state directories, titles, debugging ports, process identities and windows are campaign-owned. Only campaign-owned HANNI HWNDs are captured with validated PID/creation identity; no desktop-rectangle fallback. One native executor at a time. No installation, global DPI changes, microphone/camera activation or new model loads. Initial actual app sessions target the disposable original backend because mounted views may initialize stores and monitors even on GET.

Live-owner backend observations are bounded read-only projections. Tokens and private content are not persisted in reports. Relevant owner states are compared with authoritative services and endpoint identity. Startup/shutdown and sensitive controls are tested against owned sessions only. A failure to authenticate or a resource admission denial is a documented blocker, not an offline-node or successful-model inference claim.

## Freeze and verification

Archive original production source, assets and native artifact identities before any fixes. The independent verifier privately freezes prospective functional holdout inputs and answers before production changes. Engineers and manager do not inspect private answers. Development screenshots and independently reproduced development failures may guide repair; final holdout is executed once against a whole-source final freeze. No tuning or rerunning using final answers. Each implementation/verification cycle receives a checkpoint and concrete screenshot-supported scoring. Original defects must be independently reproduced before repair approval.

## Visual criteria and thresholds

Use the exact request in REQUEST.md. Score every implemented primary screen, overall design and typography out of 10, and AI-template appearance out of 10 (lower is better). Overall must exceed 8.5, each primary screen must reach 8.6 and AI-template appearance must be at most 2. Font comparisons must precede a permanent font change; at least five alternatives if current typography remains below threshold. Report untested Windows scaling levels and blocked controls explicitly. Never raise a score solely to pass acceptance.

## Resource budget

Existing model/controller processes remain running. At initial inspection Windows had approximately 1.14 GB available RAM (96.6% used); original model admission thresholds remain unchanged. Use one bounded native session and one disposable backend at a time, no new inference server or stress workload. Recheck memory before launch, impose bounded timeouts, and stop only owned QA processes on resource or timeout failure. Real inference is attempted only through the original resource and privacy gates; no mocks are promoted to live inference proof.

## Preservation

Campaign 4–7 source and evidence, earlier consumed holdouts, owner files and existing uncommitted changes are protected. Campaign 8 output lives under its own directories. No commit or staging is authorized by this request. Final report distinguishes confirmed passes, failures, blocked dependencies, unsupported features and not-run physical tests.

## DPI receipt correction

The first manager preflight was DPI-unaware and returned virtualized 96 DPI / 1536 × 960. The actual owned native HWND and DPI-aware capture process report 120 DPI (125%). Preserve the original receipt as a measurement discrepancy; use the native HWND and DPI-aware display receipt as authority. Setting process DPI awareness affects only the measurement process and does not change Windows display settings. Requested initial logical window dimensions and measured physical capture rectangles are reported separately.

The user explicitly reports microphone and speakers unavailable and requests that supervised wake-word, playback and interruption tests be recorded as blocked while software checks continue. Do not prompt again or activate physical audio. Device enumeration and software voice-state/control outcomes cannot establish physical success.
