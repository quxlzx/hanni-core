# HANNI Reliability & Intelligence V2: architecture audit

Authoritative starting revision: `791bdab`. Audit and baseline were completed before production edits on 2026-10-09. This project extends the existing pipeline; it adds no replacement model, registry, executor, approval queue or capability surface.

## Current request path

Keyboard/dashboard and attentive voice adapters construct the configured local client and original registry in `cli.py`. `TextSession` supplies conversational history and fixed system policy. `_wrap_mcp_session` attaches the existing MCP Hub runtime to that registry, then creates `McpHost` and `McpToolSession`; memory wraps the same session, and dashboard ChatSession wraps it for streamed history. Voice capture/relevance/attention feeds this conversation interface. Memory extraction/retrieval and screen/voice permissions remain separate existing boundaries.

`ToolRegistry` has 172 default built-in definitions, plus explicitly registered desktop management and approved imported MCP adapters when present. Metadata-only evaluation registries replace handlers with execution-denying stubs and synthetic Google availability. Those evaluations prove retrieval, not live provider access or execution. `LocalCapabilityDiscovery` lives in `tools/capabilities.py`; there is no `tools/discovery.py` in this baseline. It caches by registry revision, with weighted lexical overlap, aliases and curated routes. `McpHost` resolves existing safety/action/date/context rules, retrieves a bounded menu and preserves original external schemas/definition hashes. Its fallback requires lexical score/overlap and normally exposes at most two candidates. Diagnostic/domain rules can override ranking and exclude useful unfamiliar matches.

The resident Qwen3.5-4B Q4_K_M model receives selected original schemas; configured context is 16K, output ceiling 768 tokens, three tool rounds and an eight-tool ceiling. `McpToolSession` maps selected wire names back to existing capabilities and calls `McpHost.call`. Host eligibility and stale external-definition guards precede the original registry. Registry execution retains argument validation, profile/confirmation checks, emergency stop, foreground/workflow admission, mutation serialization, handler and private audit. External MCP calls retain their exact original names, approved hashes, transport bounds and cancellation.

`CompletionLedger` tracks requested clauses but generic `ok:true` may mark a task complete without distinguishing an action receipt from outcome evidence. Successful calls are deduplicated, while failed/ambiguous writes can be reissued in later model rounds. Email/calendar/Spotify fast paths do not all pass through a common verification observer. App launch receipts can prove process creation or acceptance without proving a visible window. Calendar creation can return an ID while filling missing schedules from the request; its handler can then label the result verified despite `created_but_not_reverified`. Retry/timeout metadata exists without a uniform executor-wide recovery policy.

HANNI OS Activity currently projects tool-audit executions as completed/failed; authenticated Agents also presents that history. There is no durable request-level execution/verification timeline. Existing fixed desktop operations remain UUID/payload-bound and confirmed; no generic frontend tools/call endpoint exists. Persistent memory/workspace and provider credential stores remain original components.

## Measured development evidence

Worker 1 reproduced required menus on 194 historical **model-tool scenarios** loaded from `evals/llm_tools/cases.jsonl` and 264 curated schema/menu probes from `evals/llm_tools/capability_coverage_v1.jsonl`: required-menu recall is 100% on those development sources. These are distinct from the verifier's graded routing corpus: `evals/routing/cases.jsonl` has 1,131 cases, 1,129 strict passes and mean score 99.590/100. Raw lexical discovery on the two model-tool scenario sets is weaker (75.12% and 80.30%). On a separate explicitly **development** wording probe, 23/35 tool requests have sufficient current menus (65.71%); 4/5 no-tool decisions are correct. A generic BM25/character-fuzzy prototype retrieves 34/35 tool menus (97.14%) with a dynamic mean of 2.45 candidates, but fails all five no-tool cases without the original host gates. A metadata latent-SVD alternative adds no unfamiliar recall and is not justified. These observations motivate a bounded hybrid fallback, not removal of policy/date/no-tool boundaries or a claim of pretrained semantic embeddings.

The baseline coverage matrix has one row per 172 default capabilities, explicitly distinguishing test-source references, measured metadata retrieval and historical model-case coverage from actual execution/verification. Of the 132 model-facing capabilities in its fixture, 74 lack a required-tool historical model scenario. Existing test references do not establish successful real execution.

The independent verifier created a separate sealed 60-case final holdout and captured its baseline against an archived original revision. Its contents remain unavailable to implementation agents; only provenance/counts/aggregate starting measurements are recorded. No development changes may be tuned against final holdout results or examples. If exposed before source freeze, that holdout must be marked contaminated and replaced. Existing historical holdouts are not reused as independent unseen-language evidence.

## Integration contracts selected from the audit

Worker 1 owns metadata-derived ranking/retrieval and `mcp/host.py`. It will compare lexical/BM25/fuzzy alternatives, preserve existing deterministic safety/date/action rules and add confidence/margin-based bounded candidates only where supported by development evidence. Ranking filters eligibility first, rebuilds by registry revision and preserves imported IDs/hashes/disabled withdrawal. No new phrase-to-tool lists or benchmark exceptions.

Worker 2 owns additive reliability observation around the original executor/session, verification and Activity UI. `ToolContext.reliability` defaults to None; `ToolDefinition.retry_safe` defaults false. The original permission gates remain authoritative for every execution and verification read. At most one additional retry requires an explicitly opted-in low-risk built-in idempotent read and a known transient/retryable error; writes, destructive requests and imported tools are not automatically replayed. Every attempted write, including an ambiguous failure, is deduplicated within the conversation.

The shared service uses context-local request/task correlation, accurate lifecycle events, scoped verification and bounded private local trace storage. It persists no raw prompt, arguments, result bodies, file paths, calendar content or hidden reasoning. A successful read proves only its returned snapshot; an action receipt is not independent outcome verification. Unsupported verification reports uncertainty. Actual pending approval is distinguished from a rejected request needing confirmation; no fabricated live approval queue is added.

Root owns original factory/CLI/chat correlation, authenticated read-only `/api/executions`, package registration, integration, documentation and checkpoints. The service is reused per resolved data directory and opens its store lazily, preserving metadata-only evaluation isolation. Activity keeps existing audit history and adds expandable request/step evidence from actual backend events. The independent verifier owns the untouched final holdout, old/new comparison, coverage evidence and actual native UI review; it implements no production features.

Worker 2's planned 40 controlled development workflows cover applications, diagnostics, files, calendar, tasks/memory, voice/screen boundaries, real SDK MCP and multi-step recovery. They exercise original menus/registry with explicit fixtures and independent outcome assertions. Deterministic test model selection is disclosed and measured separately from actual configured-model runs. The final report must give sample counts, identical-condition comparisons, uncertainty and failures rather than assume aspirational targets.
