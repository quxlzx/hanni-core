# Development repair proposal under the collection freeze

This is a proposal, not an implementation checkpoint. The original 370-case live development collection is still running on held production, harness, configuration and fixture source. No production repair, fixture rewrite, extra inference or test workload was performed while preparing this document. All examples below are completed development receipts; final queries and answers remain untouched.

## Same-turn referents and negative reasoning constraints

Completed receipts expose a general separation error. `c1-dev-process_cpu-05` routes its symptom and its requested per-process leaders separately; the second fragment loses the CPU subject and becomes a `system.stats` obligation. `c1-dev-process_cpu-10` loses the inspected PID in its measured-details continuation and adds unrelated `file.stat`. The completion ledger therefore appends an unverified suffix after successful evidence for the actual requested process. Those are observable host bookkeeping faults, separate from how the real model phrases its answer.

`c1-dev-gpu_observation-02` turns a prohibition on inferring GPU facts from CPU data into another CPU read obligation. `request_intent` recognizes several forbidden execution verbs, but lacks reasoning-constraint verbs such as infer, assume or attribute. A prohibited inference is not an independent observation request and should not create a ledger task.

The next repair cycle should independently reproduce fresh variants before changing code. Candidate scope remains the shared request interpretation, original `McpHost.route` and completion ledger. The parsing contract should distinguish an independent positive operation from a same-target refinement or an inference constraint, preserve explicit same-turn subjects/source scopes for dependent clauses, and build ledger obligations from those same interpreted operations. A pronoun cannot authorize a new source, grant a permission, or supply a missing owner path. Two genuinely independent positive operations must still require separate verified receipts; read/action mixtures must retain original blocking and confirmation behavior. Changes should not depend on any development phrase, app name, measured number or expected answer.

Completed `c1-dev-retained_history-02` also loses the original owner's CPU subject when the next request asks which process is using most of it. The host returns an empty menu and the model supplies an unsupported process/percentage. The empty retrieval and the fabricated measurement are separate findings. A narrow original-host context bridge can use a unique recent owner resource subject to retrieve the original matching ranking, while requiring new actual evidence for the answer. Assistant prose is not resource authority; unrelated intervening owner turns, multiple resource antecedents and quoted instructions must not supply an invented subject. Educational and conversational empty-menu paths must remain available. The Manager has limited this cycle to the existing host/context scope; no blanket fallback or narrative guard change is authorized.

The Engineer prepared 38 independently worded cases in `tests/unit/test_campaign1_dependent_clauses.py`, without executing them during collection. These cover same-target CPU/PID/measurement refinements, infer/assume/attribute prohibitions, positive requests following prohibitions, genuinely independent read receipts, failed/unverified receipt preservation, original mutation denial, quoted literal preservation and eight recent-history resolution/ambiguity controls. Independent pre-fix reproduction and the failing run must precede any production repair.

## Original process verification contract

Source inspection found a production mismatch independent of the model and controlled source. `tools/system.py` `_process_list` returns `pid`, `name` and `memory_percent`. `reliability/verification.py` instead requires `memory_mb` for `process.list`. Valid original handler rows therefore fail verification. This differs from the authored `process.top_memory` source's separate missing `rss_mb` field.

After collection, independently reproduce the `process.list` mismatch by exercising its original handler with controlled `psutil` process records, passing the actual returned result through the original verifier. A narrow verifier correction should validate the original metric, retaining strict numeric type, finite/range checks, required row identity and conservative treatment of incomplete data. A test must cover valid original rows, malformed/wrong-type/nonfinite rows and the relevant empty/unavailable result semantics. It must not fabricate verification status or weaken authority. The Manager has accepted this possible `reliability/verification.py` scope extension only for a separately verified post-development repair.

The independent reproduction is already preserved at `data/campaign1-verifier/process-list-contract-before-repair/results.json`. The Engineer has prepared 22 focused cases in `tests/unit/test_campaign1_process_verification.py` and has not run them during collection. The proposed production diff is limited to choosing `memory_percent` for the `process.list` metric and requiring its value to be at most 100, in addition to the existing strict numeric type, finite value, nonnegative value, nonempty row list and nonempty process-name checks. `process.top_cpu` keeps `cpu_percent`, `process.top_memory` keeps `rss_mb`, and status/provenance/permission behavior stays unchanged. Empty evidence and failed execution remain unverified.

## Named-process CPU requests

The original `process.find` handler in `tools/overview.py` filters by requested name and returns matching PID/name, `memory_gb` and `running_minutes`. It does not supply CPU percentage. A selected `process.find` tool alone cannot substantiate the CPU answer requested by `c1-dev-process_cpu-08`, even though the current synthetic source includes a CPU field. The frozen source also returns `FixturePreview.exe` for a request about Paint; the model's renaming of that row is a real grounding failure, and the unrelated result is separately a dependency-semantic mismatch.

The original `process.inspect` proves PID existence; it does not supply CPU/RAM measurements either. A later generic routing repair could expose bounded original `process.top_cpu` evidence for a named-process CPU question, but that supports a measurement only when the requested process appears in the returned ranking. An absent process cannot be assumed idle or stopped. If identity or the measurement is unavailable, the assistant must state that limitation. Neither a host nor a fixture should bind the owner's requested application name onto an unrelated returned process or infer CPU from a memory/existence result. Whether existing evidence satisfies the request must be measured using actual original controller turns, not credited from metadata availability or a synthetic extra field.

### Time and local task sources

The controlled `time.now` seam currently formats the declared local clock and then binds argument fields, without actually applying `timezone`, `kind` or `day_offset`. Completed `c1-dev-clock_and_dates-03` returns the local -04:00 clock for a Seoul request, and `-06` returns the current date for tomorrow. This is a source-seam defect, distinct from the real model saying 2024 in an empty-menu current-year question.

The next source version should exercise original `timekeep._now` with a module-local controlled clock, rather than independently recreating its formatting. Its timezone selection, kind checks, day-offset bounds and message/data semantics must remain original. In particular, `requested_date` changes for a relative date request, while the original `date`/`iso` still describe the measured current instant. Do not patch the process-global wall or monotonic clock: adaptive freshness, resource admission and timing must keep their real clocks. Record controlled-clock provenance explicitly. Independent checks should cover another IANA zone, a date boundary, both day-offset directions and rejected timezone/kind/offset arguments.

The actual original `todo.get` and `todo.complete` contracts require **string** IDs; `tools/todos.py` stores TEXT primary keys and generates `uuid4().hex`. The held runtime `registry-contracts.json` independently confirms this. Integer model arguments should remain typed failures, not be converted into strings or accommodated by changing the schema. A controlled task source must keep an opaque ID consistent between list rows, requested records and mutation/readback receipts. Match requested IDs against a fixed generic synthetic record inventory; unknown IDs stay not-found. Do not bind an argument into one top-level ID while retaining a different nested task ID, or rename unrelated records to fit the request. These source corrections must be versioned; no frozen development/final objective is relabeled.

## Unit argument contracts and normalization

Completed actual original-handler development calls reject full-word `kilometers`/`meters` and `KiB`. This is not a JSON type failure: the registered fields accept strings, while `compute.py` only looks up the finite `_UNITS` keys. Metadata already advertises kilometers and gigabytes, which do not appear as accepted keys. Before changing production, retain the original real-handler failures and independent fresh spelling/control reproductions.

The proposed narrow `tools/compute.py` repair introduces explicit unit-token aliases onto the existing tables, leaving every original factor and conversion formula unchanged. Natural metric names can map to their existing symbols, including consistent American/British singular/plural spellings. Explicit IEC tokens and names (`KiB`/kibibytes, `MiB`, `GiB`, `TiB`) map to the existing binary factors. Legacy `KB`, `MB`, `GB` and `TB` remain 1024-based; their spelling and full-word equivalents must be described as legacy binary semantics. Do not silently substitute decimal factors, conflate bits with bytes or add conversions between dimensions.

Normalization should keep the existing case-insensitive and surrounding-whitespace behavior. Unknown/nonsense tokens and incompatible dimensions continue to fail. Input metadata should declare all three fields required and non-null, and describe the finite legal unit vocabulary and binary conventions. A strict lowercase-only enum would break existing case/whitespace inputs; use an honest field description unless schema and original argument normalization can agree without broad base-registry changes. No model setting, global parser, numerical conversion or permission change is proposed.

The Engineer has prepared 40 cases in `tests/unit/test_campaign1_unit_arguments.py`, without running them during collection. They cover advertised full words, consistent family spellings, IEC units, preserved legacy factors, temperature/case/whitespace behavior, unknown and incompatible units, missing/null/invalid numeric arguments and model-visible field metadata. Numeric expectations are independently specified; they are not generated from the implementation tables or final answers. All pre-fix and post-fix evidence remains for the later authorized repair cycle.

## Read-response grounding and model limits

Completed actual responses describe a 36.5% CPU snapshot as more than half, infer exporting headroom from a snapshot, rename an unrelated process, and infer a stable battery charge rate from a plugged-in percentage. These are real model response failures despite the existing instruction to distinguish measurements, possibilities, historical trends and unknowns. The existing `_guard_answer` enforces action receipts and result verification status but does not validate arbitrary entailment in a successful read narrative.

A generic evidence boundary may help with well-defined structured contradictions, missing identity or unsupported completion claims. It would need independent development reproductions, a bounded original-result representation, and tests showing that it preserves valid derived facts and unknowns. A phrase blacklist or substitutions for benchmark numbers would not establish grounding. Free-form causal explanation and arithmetic interpretation can still fail in the 4B model; this proposal does not claim that a small host patch can repair every model error. Any expansion into `mcp/session.py` or response handling requires the Manager's explicit scope decision after the complete development evidence and independent failure review.

The Manager has explicitly excluded `mcp/session.py` and blanket narrative guarding from this repair cycle. Unsupported causal and quantitative claims remain measured model limitations. The approved work is the narrow routing/context/completion interpretation, original process metric verification and unit argument contract alignment above; it cannot replace real answers with expected ones or change sealed objectives.
