# Tool Intelligence V1 freeze decision: not frozen

The development gate passed, but the single locked [Holdout V2 report](../evals/llm_tools/results/qwen_holdout_v2_locked_once.json) passed **45/72 tasks (62.50%)**. This is below the roadmap's 80–85% blind target. Qwen3.5-4B remains the production model; no new capability families were added.

The dominant issue is routing generalization. Before any model inference, the holdout audit found 24 missing or incomplete MCP menus, including 12 empty menus. Those 24 cases all failed strict task success. Ten of 20 diagnostic and five of eight mixed-domain holdout requests had routing misses. New phrases such as “folders open at a snail pace lately,” “performance gets rough the second i unplug it,” and “time until my next class and top ram hog” expose gaps that the tuned Language V3 development set did not reveal. The frozen 1,087-case routing regression remained at 99.91%, and Language V3 was 100% on its development phrases; those numbers did not predict this blind result.

The official report has three additional model-reasoning failures among 48 cases with sufficient routing. One answer asserted unverified GPU throttling; another misstated a Calendar time window. [Post-run oracle review](../evals/llm_tools/results/holdout_v2_postrun_oracle_audit.json) found the third to be a scorer false negative: Qwen correctly reported CPU usage of 20%, while the inherited `MIX-005` answer pattern incorrectly expected `24`, the mocked GPU temperature. The locked report and scorer were not changed or rerun. Manually adjudicating that one case yields 46/72 (63.89%), still well below the freeze target. The conditional 45/48 success rate when routing was sufficient is useful for failure attribution, not a replacement for the overall task-success rate.

Holdout safety was 4/4, hallucinated tools 0, forbidden calls 0. The benchmark used only deterministic synthetic results; no real capability handler ran. The [holdout lock](../evals/llm_tools/holdout_v2.lock.json) was written before inference, and its corpus hash and the [development freeze](../evals/checkpoints/pre_holdout_v2.json) remained intact afterward. No router, prompt, fixture, or evaluator was tuned from this holdout.

The next development step is to create a **new, separate** owner-language development set covering broad diagnostic paraphrases, app launch verbs, Calendar free-window wording, mixed clauses, and educational no-tool questions. Use it to improve the existing bounded intent-prototype router and correct the `MIX-005` development oracle, while keeping Holdout V2 immutable as a historical checkpoint. Re-run the development gate, then create a new blind holdout only after the revised implementation is frozen. Do not claim Tool Intelligence V1 is ready from the development score alone.
