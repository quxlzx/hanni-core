# MCP Hub implementation checkpoints

## M1: architecture and baseline (2026-10-09)

Baseline: `edd9a043b45d1b6c7ef056cae4460fc5c82c8468`. Independent verification: 882 pytest cases passed, 2 skipped, 17 passing subtests; frontend type check and production build passed. Detailed evidence: [baseline review](mcp-hub-reviews/baseline.md).

The installed official MCP SDK is 2.2.0. HANNI already has `McpHost`, `McpToolSession`, `ToolRegistry`, revision-aware `LocalCapabilityDiscovery`, permission profiles, emergency stop and tool audit. These remain the execution authority. Existing MCP support exposes local capabilities; it has no outbound client or persisted external definition approvals. The dashboard launcher and CLI controller run in the same process, allowing a single connection manager to attach to the actual controller registry without IPC or a replacement router.

Ownership: Worker 1 implements connection/transports, transactional persistence, endpoint and credential safety, original-schema adapters and minimal registry/host changes. Worker 2 implements the MCP Hub and Settings integration. The primary agent owns authenticated dashboard operations, controller lifecycle binding, navigation and integration. The verifier owns independent tests, native screenshots and reports. The three agents are actual existing Codex subagents. No unrelated model/benchmark files will be edited.

Contract: `MCPManager(data_dir, registry=None)` provides snapshots, add/update/connect/refresh/reconnect, server enable/disable/disconnect/remove, hash-bound per-tool approval/disable, import preview/import and secret-free export. `attach_registry` binds imported capabilities to existing registries. Construction never starts a process or connects a server. Disabled servers and tools stay disabled. Schema/description/security metadata changes revoke approvals. Server identity and original external tool name are separate from stable namespaced capability IDs.

Authenticated private HTTP: `GET /api/mcp`, `GET /api/mcp/export`, and `POST /api/mcp` with `{id, operation, data, confirmed:true}`. Fixed operations: `add`, `update`, `test_discover`, `refresh`, `reconnect`, `enable_server`, `disable_server`, `disconnect`, `remove`, `approve_tools`, `disable_tools`, `import_preview`, `import`, `export`. No generic tool-call endpoint. Connection dialogs display exact command/arguments or endpoint before an explicit connection approval. Import preview precedes import and cannot launch anything. Requests remain payload-bound and deduplicated.

Approval to connect, definition approval and execution confirmation are distinct. The current model MCP host is read-only by default and always submits unconfirmed requests. Imported writes must remain subject to the original policy, with an explicit trusted confirmation path if supported; enabling a definition never implies authorization to execute a write. Unknown tools remain restrictive.

Implementation checkpoints will record source files, actual checks, remaining issues and next steps. Native GUI review uses the new five categories, each out of 2: typography/hierarchy, layout/density, spacing/consistency, professional appearance and interaction polish. Acceptance requires visual quality >8.5/10, AI-template appearance <=2/10, passing security checks and real imported execution through the original controller. Historical visual scores do not establish this feature's acceptance.

Completed files: this architecture/checkpoint document and `docs/mcp-hub-reviews/baseline.md`. No implementation edits at this checkpoint. Next: implement M2 transports/store/lifecycle and M3 registry adapters; build M4 UI against the fixed authenticated API.
