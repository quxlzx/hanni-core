# Capability description and schema audit

The [registry snapshot](../evals/llm_tools/results/capability_description_audit.json) records descriptions and argument schemas for all 150 registered capabilities. In the current model session, 114 are model-facing and 36 are intentionally unavailable. The longest description is 199 characters, so the catalog does not contain a large single-description outlier.

The main ambiguous pairs are distinguishable in the current text: `disk.usage` reports capacity, `process.top_disk_io` reports current per-process I/O rates and explicitly disclaims health, and `device.disk_health` reports SMART/media state. `system.stats` includes GPU sensors when available; `system.performance` is a broad CPU/RAM/storage-capacity snapshot that explicitly disclaims disk I/O, GPU load and power-plan conclusions. `gpu.memory` is total VRAM, while `gpu.top_processes` identifies consumers. `spotify.launch` opens the client; `spotify.play_pause` toggles playback. `google_calendar.agenda` lists a range; `google_calendar.next` gives the next future event and a local interval.

Two wording gaps remain: `gpu.memory` emphasizes loading another model even though gaming VRAM questions also need it, and `app.open` takes a generic `app` argument rather than `app_name`. Renaming the argument would break an existing public schema, so it should be treated as a versioned compatibility change. These descriptions should be tested in the separate capability-coverage corpus before any freeze; the main 150-case LLM eval currently requires only 17 of 114 model-facing capabilities in at least two cases.
